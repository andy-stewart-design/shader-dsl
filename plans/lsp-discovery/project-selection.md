# Phase 1 contract — selecting a TypeScript project

Status: proposed for review; implemented **only in an isolated resolver**, not yet wired to the LSP or Zed. The server still assumes a single workspace `tsconfig.json`. The current TypeScript 7.0.2 `API.parseConfigFile()` returns file names **without reporting config errors**; use a project snapshot's `program.getConfigFileParsingDiagnostics()` to distinguish invalid configs from clean projects. Do not treat a filename returned by a malformed config as proof of a valid project.

## Selection rule

Only local `file:` URIs for existing `.shdr.ts` files are eligible. Canonicalize the worktree roots and document path via `realpath`; a symlink into a worktree uses the target's project, while a symlink **out** of every worktree is outside the supported boundary. For overlapping worktree folders, use the deepest canonical containing root. Search from the document's canonical directory upward through that root **inclusive** for the **nearest config that includes the file**. Continue past configs that exclude it, but do not traverse past the worktree root or silently skip an invalid config. This follows the editor-ownership change described in the [TypeScript 5.7 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-7.html#searching-ancestor-configuration-files-for-project-ownership). TypeScript 7's parsed configured-project root-file list (rather than a homemade interpretation of `include`/`exclude`/`extends`) determines membership. In TypeScript 7.0.2, opening a file alone selected an inferred project when the nearer config excluded it; explicitly opening the including parent project selected that parent. Phase 2 must pass the resolver's chosen config explicitly to the adapter. A missing/unsaved file is unconfigured until it exists on disk; LSP in-memory changes to an existing file still use that file's configured project.

| Input / ancestor configs                                                | Result                                                     | What the editor must eventually show                                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Nearest valid config includes the shader                                | `project(configPath, canonicalFilePath, worktreeRoot)`     | Adapter diagnostics/hover for that config, at original URI/ranges                                    |
| Nearest excludes it; an ancestor within the worktree includes it        | `project(ancestorConfigPath, ...)`                         | Check using the including ancestor's options, not an inferred project                                |
| Every encountered valid config excludes it                              | `excluded` (nearest excluded config path)                  | Explicit "no tsconfig.json in this worktree includes file" status; no fake clean diagnostics         |
| Encountered config has parse/option errors before an including ancestor | `invalid-config` with TypeScript config diagnostic code(s) | Explicit config error; do not silently skip a broken project                                         |
| No config within the worktree                                           | `no-config`                                                | Explicit "no tsconfig.json in worktree" status; no inferred project advertised as checked            |
| File missing on disk (including a new, unsaved shader)                  | `not-on-disk`                                              | Explicit unchecked state until a later open/change after save                                        |
| Shader URI outside all worktrees, or symlink target outside             | `outside-workspace`                                        | Explicit unchecked state; don't check against another worktree                                       |
| Ordinary `.ts`, non-file URI, or invalid URI                            | `ignored`                                                  | No Shdr diagnostics or hover; ordinary `.ts` remains the native TypeScript provider's responsibility |

Messages are single actionable sentences with the reason and relevant file/config path. Avoid process-internal names or virtual-source offsets. Phase 2 must choose an LSP-visible transport for the unchecked/error status (for example, a configuration diagnostic on the document and a server log), clear prior shader diagnostics when ownership becomes invalid, and test that the error cannot be mistaken for a clean file. Ordinary `.ts` must receive **no Shdr message**.

## References, versions and lifetime

- A `tsconfig.json` listing project references can own a shader only if that **config itself** includes it; otherwise search upward for an including ancestor. A nearer referenced project's own config is found normally when the file is under its directory. Unlike the full TSServer project-ownership search, do not traverse references from a solution config or adopt a referenced project outside the containing worktree; that is a later feature.
- A project identity is its canonical config path. On multiple worktrees, independent configs retain independent adapters; an open document belongs to exactly one selected config. Dispose its checked document on close or ownership change, and dispose an adapter when no documents use it. A resolver can keep its TypeScript API session for its lifetime but must release transient snapshots/projects; Phase 2 owns adapter caching.
- LSP document versions order source edits **per URI**. A distinct monotonic project/config epoch invalidates cached checking for affected documents when config/project files change; never use a constant `projectVersion: 1` after such a change. On a project switch, clear stale diagnostics before publishing results for the current document version. Out-of-order incoming edits remain ignored.
- React to `workspace/didChangeWatchedFiles` for config changes (including inherited configs) and relevant project file create/delete/rename when the client sends it, then re-resolve and republish affected open shaders. Also re-resolve on subsequent Shdr open/change so clients without watchers need **no window restart**, though immediate refresh on a silent filesystem change is not promised. Define the watch subscriptions and verify Zed's actual notifications in a later phase rather than assuming the editor supplies them.

**Phase 1 gate:** selection tests exercise two configs, nested/ancestor exclusion, bad config, missing config/file, references, root versus nested worktree, multiple worktrees, ordinary `.ts`, non-file URIs and symlinks. These tests validate the resolver, **not** protocol notifications or real-editor semantics. Phase 2 must implement the promised error visibility, versioning and refresh behavior before claiming the whole contract is delivered.
