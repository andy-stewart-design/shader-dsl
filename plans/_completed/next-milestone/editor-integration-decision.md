# PR 3 editor integration decision (Phase 3.3)

**Decision:** Keep the existing VS Code `DiagnosticCollection` and `HoverProvider`, and retain the shared stdio LSP as the _Zed feasibility path_. Both use `@shdr/language-service`'s `TypeScript7EditorAdapter`; this is **one semantic implementation with two editor transports**, not two shader checkers. Do not switch the working VS Code fixture to LSP in this PR or present the local Zed dev extension as shipped support. Revisit a single LSP transport for both editors only after it has a distributable runtime, project discovery, and performance/error-handling tests. Defer semantic tokens, completion, rename, and general formatting integration.

The Zed goal for **recognition and lexical highlighting** was met in a real editor, and **diagnostic/hover feasibility** was demonstrated. The goal of **installable, generally usable Zed semantic support is not met**. A screenshot of one fixture is not a cross-project claim.

| Behavior                               | VS Code 1.127.0 development host, fixture folder                          | Zed 1.21.0 dev extension, fixture folder                                                                        | Zed 1.21.0 dev extension, repository root                                       |
| -------------------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `.shdr.ts` language / lexical coloring | `shdr-typescript`; TypeScript TextMate scopes verified                    | `Shdr`; limited TypeScript tree-sitter query verified                                                           | `Shdr` recognition works; not a full TypeScript query                           |
| Shader diagnostic / hover              | Adapter-backed, real-editor checklist and tests pass                      | Same adapter via stdio LSP; one mapped invalid-operation diagnostic and `Expr<Vec2<F32>>` hover verified        | **No Shdr LSP**: launcher rejects this worktree; no Shdr diagnostic/hover claim |
| Ordinary `.ts` ownership               | Built-in TypeScript, manually checked; Shdr tests do not assert its hover | Remains TypeScript in fixture                                                                                   | Remains separate from the Shdr language; no general project test                |
| Formatting                             | No Shdr formatting provider verified                                      | Fixture `.zed/settings.json` invokes root Prettier through `pnpm` and formats layout; format-on-save unverified | Prettier formatting observed, but does **not** imply a running Shdr LSP         |

The Zed dev launcher deliberately checks the fixture's `package.json` and uses `../../packages/lsp/dist/bin.mjs`. Opening the repository root with `zed -n .` therefore produces a Shdr server startup error; opening the fixture from the repository root with `zed -n "$PWD/apps/editor-fixture"` is the **only verified LSP worktree**. Rebuilding the dev extension stops an active LSP; reopening the fixture worktree restored it in the manual retest. Do not infer semantics from highlighting or successful formatting. Standalone `shdr check` covers shader syntax/semantics but not ordinary TypeScript outside the callback.

## Requirements before wider integration

1. **Projects:** Discover the containing `tsconfig.json` per Shdr file from the actual worktree (including a repo root with multiple packages), determine behavior for no config, multiple roots and project references, and keep a separate checked-document/project cache per config. Make configuration and file changes refresh diagnostics without a window restart. Verify on a second non-fixture project and with `.ts` files still owned by TypeScript.
2. **Responsiveness:** Move synchronous TypeScript 7 checking off the server event loop / VS Code extension host; add cancellable or superseding requests, consistent document/project versioning, bounded caches and recovery from project/checker errors. Protocol tests for stale replies and real-editor tests for rapid edits are required; rejecting stale _incoming_ versions alone is insufficient.
3. **Distribution:** Replace the hard-coded relative `dist/bin.mjs` and fixture manifest check. Choose and test an explicit Node/runtime strategy and a reproducible bundled server artifact from a clean install; make the Zed extension acquire or locate the matching server, report missing runtime/config errors, and test install, update, restart and removal without repository `node_modules`. Publish neither the extension nor the server until those paths work. Decide separately how to ship and upgrade the VS Code extension, which is also currently a fixture.
4. **Editor quality:** Test real Zed and VS Code versions against the pinned TypeScript 7.0.2 API, mapped diagnostics, hover, `.ts` isolation and lexical highlighting. Document layout formatting separately (the nested fixture needs an external Prettier setting; VS Code has no Shdr formatter). Decide whether to reuse/track Zed's complete TypeScript highlight query instead of promising parity from the current small query.

**PR 3 boundary:** The current PR may merge the VS Code grammar, the clearly labeled local Zed spike and the private LSP protocol tests with this decision. It must not claim a production cross-editor LSP, root-workspace diagnostics, a published Zed extension, or a VS Code formatter. Phase 3.3 makes no runtime changes; the items above are follow-up work, not hidden acceptance criteria for the current milestone.
