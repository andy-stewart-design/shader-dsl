# Zed Shdr extension spike (repo-local)

**Status: locally verified in Zed 1.21.0 on macOS; not published or shipped.** The [highlighting screenshot](verified-zed-1.21.0.png) shows lexical colors and the **Shdr** language indicator. A separate [diagnostic screenshot](verified-lsp-diagnostic-zed-1.21.0.png) and [hover screenshot](verified-lsp-hover-zed-1.21.0.png) demonstrate the Phase 3.2 **repository-local** language-server spike, which uses the same TypeScript 7 checker as the VS Code fixture.

Zed's built-in TypeScript language uses the `typescript` tree-sitter grammar (see its [config](https://github.com/zed-industries/zed/blob/main/crates/grammars/src/typescript/config.toml)). The extension registers a _separate_ `Shdr` language with the more-specific `shdr.ts` suffix and references that built-in grammar rather than downloading or writing another parser. Zed language queries are loaded per language: they do **not** automatically reuse TypeScript's full [`highlights.scm`](https://github.com/zed-industries/zed/blob/main/crates/grammars/src/typescript/highlights.scm). The small tree-sitter query here only colors the fixture's ordinary TypeScript tokens (keywords, calls, properties, strings, numbers, comments, operators); it is **not** a shader regex grammar or a semantic checker. Reusing all built-in TypeScript highlighting without vendoring and tracking its queries remains an open packaging constraint.

## Reproducible manual check

1. Confirm `zed --version` (spike used 1.21.0). Open Zed in a disposable profile if possible, so the existing user profile's extensions/settings are untouched. If Zed is already running, its CLI may route the file to that instance rather than honor `--user-data-dir`.
2. Run `pnpm build` from the repository root. The Rust/Wasm launcher rebuild requires Rust with the `wasm32-wasip2` target (Zed can install it when rustup is available). In Zed's Extensions screen, select **Install Dev Extension** and choose `extensions/zed-shdr`, or **Rebuild** if already installed at that path. If previously installed from `experiments/zed-shdr`, remove that dev installation and install it again from the new path; the old dev symlink will be broken by this move. Consult **zed: open log** if compilation fails. No new Tree-sitter grammar is downloaded. **Rebuild can stop an already-running Shdr LSP; close and reopen the worktree afterward.**
3. Separately open `zed -n .` and `zed -n ./apps/editor-fixture`. Both worktrees now resolve the same built local server. In each, open `expanded.shdr.ts` and confirm the language indicator reads **Shdr** (not TypeScript), with colored TypeScript tokens. Open `ordinary.ts` and confirm it remains **TypeScript**. From the repository-root worktree, also check `packages/lsp/test/fixtures/project-b/invalid.shdr.ts` (a different `tsconfig.json`).
4. In each worktree, open `apps/editor-fixture/test/fixtures/invalid.shdr.ts` (relative to the repository root; `test/fixtures/invalid.shdr.ts` relative to the fixture). Hovering `coord.xy / coord` should show exactly one original-source diagnostic from **shdr 2769**, starting `Operator "/" cannot be applied`, without a native TypeScript cascade. Open `gradient.shdr.ts` and hover `uv` inside `vec4(uv.x, ...)`; it should show **`Expr<Vec2<F32>>`**. That file also intentionally reports one ordinary TypeScript error outside the shader callback. In the root worktree, repeat the invalid-operation and hover checks under `packages/lsp/test/fixtures/project-b`.
5. Open `apps/editor-fixture/math-builtins.shdr.ts` (or `math-builtins.shdr.ts` in the fixture worktree) and hover `mask` in `mask.x`: expect `Expr<Vec2<F32>>` and no diagnostic. Open `apps/editor-fixture/test/fixtures/invalid-math.shdr.ts` (or `test/fixtures/invalid-math.shdr.ts`) for one original-call `SHDR1209` on equal `smoothstep` edges. As before, ordinary `.ts` remains TypeScript. The repo-local Zed 1.21.0 check on 2026-09-28 observed the builtin hover and this one diagnostic in the fixture worktree; protocol tests exercise `SHDR1208` and `SHDR1209` from the same shared adapter. This is not a claim of a packaged release or general-project support.
6. Record any conflict or server startup failure rather than hiding it. The linked screenshots cover the Shdr workspace. Launcher-only checks: `node --test extensions/zed-shdr/launch-lsp.test.cjs` and `cargo test --manifest-path extensions/zed-shdr/Cargo.toml` from the repository root.

### LSP scope and setup (Phase 3.2.2)

The manifest registers `shdr-lsp` **only for Shdr**, and the small Rust/Wasm shim in `src/lib.rs` launches the built `packages/lsp/dist/bin.mjs` through Node. The **dev launcher** accepts only this checkout's repository root or its `apps/editor-fixture` worktree; it resolves the same absolute `packages/lsp/dist/bin.mjs` in either case. The repo-local [`launch-lsp.cjs`](launch-lsp.cjs) preflights the root package marker and reports a missing built artifact on stderr with a `pnpm build` instruction; stderr/log visibility depends on Zed. It does not write to protocol stdout. The stdio server selects project configs per shader (including the separate `packages/lsp/test/fixtures/project-b` project). A file-only worktree, another Zed project, or an unpackaged installation cannot start it through this dev extension; highlight recognition remains separate. This is **not** a distributable launcher or general-project support. The initial verified build used an isolated temporary Rust toolchain; future **Rebuild** actions need Rust available to Zed. The [editor integration decision and matrix](../../plans/_completed/next-milestone/editor-integration-decision.md) record the chosen integration path and wider-support requirements.

The earlier fixture editor check verified a mapped operation diagnostic, an `Expr<Vec2<F32>>` hover, ordinary TypeScript error preservation and ordinary `.ts` language ownership. Root-worktree and second-project verification are recorded separately below. Cancellation, general multi-root/distribution and switching the VS Code fixture to LSP remain out of scope. Protocol-level edge cases are covered separately in [`packages/lsp`](../../packages/lsp).

### Formatting (manual check after rebuilding the dev extension)

The language config requests Zed's `typescript` Prettier parser. After changing it, **Rebuild** the local dev extension to refresh its active configuration. Earlier, the user verified **editor: format** after rebuilding, in a repository-root workspace. But in the nested `apps/editor-fixture` workspace, Zed's automatic formatter selection did not format a deliberately unformatted `.shdr.ts` scratch file. This folder does not have its own `node_modules/prettier`, though the CLI can resolve the repository-root installation. The parser hint alone therefore should not be claimed as sufficient in this workspace.

For this **fixture workspace only**, [`apps/editor-fixture/.zed/settings.json`](../../apps/editor-fixture/.zed/settings.json) routes Shdr formatting to the repository-root `node_modules/.bin/prettier` directly. A short `sh` command uses the buffer path to find the Git root, so it also works for nested files regardless of Zed's process working directory. Run `pnpm install` at the repository root first; this is not a general-project solution. The buffer goes through stdin and the result comes from stdout; the command does not rewrite the file on disk itself. The previous `pnpm exec prettier` setting formatted a compact shader in real Zed 1.21.0 but took ~1.25 s per standalone invocation on this machine; invoking the direct executable via `sh` and `git` took ~70 ms in the same benchmark. That is **process timing**, not a measured Zed UI latency or a guarantee about synchronous LSP rechecking after format. After reopening the fixture workspace, the user confirmed **editor: format** felt substantially faster with the direct command. Format-on-save remains off. To test, change spacing around `=` or `/` rather than inserting a single blank line: **Prettier intentionally preserves one blank line**, which can make a successful format look unchanged. `pnpm exec prettier --check apps/editor-fixture/gradient.shdr.ts` confirmed the user's one-blank-line test was already formatted.

Prettier's standalone CLI also works with `.shdr.ts`: `pnpm exec prettier --write apps/editor-fixture/expanded.shdr.ts`. Both paths format layout, **not** shader semantics. This fixture setting is not a published formatter configuration for arbitrary Zed projects.

An alternate _temporary_ Zed user setting of `"file_types": { "TypeScript": ["*.shdr.ts"] }` can reuse TypeScript's complete built-in grammar **and** highlighting, but then `.shdr.ts` is TypeScript to Zed and its ordinary TypeScript language server may show incorrect shader-operator diagnostics. The dedicated-language spike isolates that conflict, at the cost of a minimal rather than full TypeScript highlight query.

## Observed results and limits

Before Phase 3.2, installing from **zed: install dev extension** switched the expanded fixture from **TypeScript** with native operator errors to **Shdr** with lexical colors and without native TypeScript underlines. The Phase 3.2 shim started one Node LSP in the `apps/editor-fixture` workspace: the invalid operation produced one mapped `shdr 2769` diagnostic, `uv` returned `Expr<Vec2<F32>>`, and `ordinary.ts` still read **TypeScript**. The checker is shared through `@shdr/language-service`; this is not a second Zed-specific checker.

**Phase 3, Zed 1.21.0 / TypeScript 7.0.2 (macOS):** After `pnpm build` and a dev-extension **Rebuild**, the Zed log showed `launch-lsp.cjs` starting with the repository-root working directory for `zed -n .` and with the fixture working directory for `zed -n ./apps/editor-fixture`. In each, the invalid fixture showed one mapped `shdr 2769` operation diagnostic without a native TypeScript cascade, `uv` hovered as `Expr<Vec2<F32>>`, and `ordinary.ts` remained TypeScript. From the root, the separate `packages/lsp/test/fixtures/project-b` config gave its own mapped [operation diagnostic](verified-root-second-project-diagnostic-zed-1.21.0.png) and `Expr<Vec2<F32>>` hover; the [root fixture hover](verified-root-hover-zed-1.21.0.png) and [reopened fixture diagnostic](verified-fixture-reopened-diagnostic-zed-1.21.0.png) were also captured. Closing/reopening **both** worktrees restored diagnostics; this is not a clean-install or external-project result.

In the root worktree, temporarily changing `project-b/tsconfig.json` to exclude its open invalid shader produced an explicit `No tsconfig.json ... includes ...` status in Zed; restoring the config brought back the mapped operation underline **without reopening**. This verifies one live local-config refresh path, not every inherited-config, new-file or cancellation scenario. A separate external rewrite of an open shader briefly left an older diagnostic hover visible even while the source had updated; closing/reopening that tab resolved it. Do not promise immediate refresh on arbitrary on-disk shader edits from this check alone. The modified config was restored.

**Extension relocation check:** After moving from `experiments/zed-shdr` to this directory, the old dev installation was uninstalled and the extension was installed again from `extensions/zed-shdr`. Zed 1.21.0 compiled the moved Wasm component; its log then showed `extensions/zed-shdr/launch-lsp.cjs` launching from **both** supported worktrees. The root `project-b` shader and the fixture-worktree shader each again displayed the mapped `shdr 2769` diagnostic. The screenshots linked above were captured before the path-only relocation; this subsequent editor check confirms the relocated launcher, not new semantic behavior.

The install created a dev-extension symlink in Zed's current user profile. Remove it through Zed's Extensions screen when finished testing. Attempting `--user-data-dir` while Zed was already running routed to the existing instance instead of an isolated profile. Packaging/runtime provisioning, full parity with Zed's TypeScript highlight queries, and performance/cancellation hardening remain follow-up work.
