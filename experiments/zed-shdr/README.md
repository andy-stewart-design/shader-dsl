# Zed Shdr highlighting spike (Phase 3.1)

**Status: visually verified as a local dev extension in Zed 1.21.0 on macOS; not published or shipped.** The [real Zed screenshot](verified-zed-1.21.0.png) shows the expanded fixture with lexical colors and the **Shdr** language indicator. There is no language server in this extension: mapped diagnostics and hovers for `.shdr.ts` in Zed are Phase 3.2 questions, not Phase 3.1 features.

Zed's built-in TypeScript language uses the `typescript` tree-sitter grammar (see its [config](https://github.com/zed-industries/zed/blob/main/crates/grammars/src/typescript/config.toml)). The extension registers a _separate_ `Shdr` language with the more-specific `shdr.ts` suffix and references that built-in grammar rather than downloading or writing another parser. Zed language queries are loaded per language: they do **not** automatically reuse TypeScript's full [`highlights.scm`](https://github.com/zed-industries/zed/blob/main/crates/grammars/src/typescript/highlights.scm). The small tree-sitter query here only colors the fixture's ordinary TypeScript tokens (keywords, calls, properties, strings, numbers, comments, operators); it is **not** a shader regex grammar or a semantic checker. Reusing all built-in TypeScript highlighting without vendoring and tracking its queries remains an open packaging constraint.

## Reproducible manual check

1. Confirm `zed --version` (spike used 1.21.0). Open Zed in a disposable profile if possible, so the existing user profile's extensions/settings are untouched. If Zed is already running, its CLI may route the file to that instance rather than honor `--user-data-dir`.
2. From Zed's Extensions screen, select **Install Dev Extension** and choose this `experiments/zed-shdr` directory (containing `extension.toml`). Consult **zed: open log** if the extension or built-in `typescript` grammar fails to register. No Rust or grammar download should be necessary.
3. Open `apps/editor-fixture/expanded.shdr.ts`. Confirm the language indicator reads **Shdr** (not TypeScript), and `import`, `const`, string literals, numeric literals, operators, and `vec3` calls have distinct lexical colors. Then open `apps/editor-fixture/ordinary.ts` and confirm it remains **TypeScript** with normal highlighting.
4. Record whether native TypeScript diagnostics or hover appear on the `.shdr.ts` file. This extension does not supply Shdr semantics, so neither mapped Shdr diagnostics nor Shdr hovers should be claimed. If native TypeScript diagnostics conflict, report the exact message and language indicator, rather than hiding it.
5. Capture a screenshot showing the **Shdr** indicator and highlighted expanded fixture, or note precisely which step fails. The verified screenshot linked above crops out other desktop windows.

### Formatting (manual check after rebuilding the dev extension)

The language config requests Zed's `typescript` Prettier parser. After changing this config, **Rebuild** the local dev extension from Zed's Extensions screen; changing the file on disk alone did not reliably refresh Zed's active language configuration. After rebuilding in Zed 1.21.0, the user reports that **editor: format** consistently formats `apps/editor-fixture/expanded.shdr.ts`. The expanded fixture on disk changed from three extra blank lines to one after the test. Earlier attempts in the same session saved without formatting, and a search for `editor: format` showed no match before rebuilding; those failures should not be presented as a confirmed workspace limitation. The screenshot of the Extensions screen shows the **Rebuild** control, not the formatting result itself.

To reproduce locally, rebuild the installed dev extension, reopen the shader if necessary, confirm the language indicator says **Shdr**, make a reversible spacing change, and use **editor: format**. Review the resulting diff. Prettier's standalone CLI also works with `.shdr.ts`: `pnpm exec prettier --write apps/editor-fixture/expanded.shdr.ts`. Both paths format TypeScript-shaped layout, **not** shader semantics. Format-on-save and published-extension behavior have not been verified.

An alternate _temporary_ Zed user setting of `"file_types": { "TypeScript": ["*.shdr.ts"] }` can reuse TypeScript's complete built-in grammar **and** highlighting, but then `.shdr.ts` is TypeScript to Zed and its ordinary TypeScript language server may show incorrect shader-operator diagnostics. The dedicated-language spike isolates that conflict, at the cost of a minimal rather than full TypeScript highlight query.

## Observed results and limits

After installing from **zed: install dev extension**, the open expanded fixture switched from **TypeScript** with native TypeScript operator errors to **Shdr** with colored keywords, string/numeric literals, calls, and operators, without those native TypeScript underlines. `apps/editor-fixture/ordinary.ts` remained **TypeScript** with its usual coloring. The status bar still reported an unrelated **Failed to run eslint** warning in this workspace; the spike does not supply Shdr semantics, diagnostics, or hover. These are separate observations, not a claim that Zed now checks shader semantics.

The install created a dev-extension symlink in Zed's current user profile. Remove it through Zed's Extensions screen when finished testing. Attempting `--user-data-dir` while Zed was already running routed to the existing instance instead of an isolated profile. This test demonstrates **file recognition and basic lexical highlighting only**; packaging for release, full parity with Zed's TypeScript highlight queries, and shared LSP semantics remain follow-up work.
